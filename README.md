# Wander Planner — Adaptive Itinerary Board

Wander Planner is a self-contained trip-planning prototype: a FastAPI backend that
builds and adaptively replans multi-day itineraries, and a single-file HTML/JS
frontend that renders them as an interactive board with a live map, a budget
tracker, and a chat assistant that can edit the plan in plain English.

There's no external LLM API wired in — the "AI" is a fast, deterministic rules
engine driving destination knowledge, disruption handling, and chat responses.
It's built so that swapping in a real model call later is a small, contained
change (see [Architecture notes](#architecture-notes)).

## Features

### Itinerary generation
- Pick a destination, trip length (1–30 days), total budget, and a set of
  preference tags (beaches, history & forts, food & cafes, nightlife, nature,
  museums, relaxed pace, adventure).
- Seven curated Indian destinations (Goa, Kolkata, Jaipur, Manali, Kerala,
  Mumbai, Delhi) ship with real activities, real costs, real coordinates, and
  destination-specific tips. Anything else typed in gets a deterministic
  synthetic itinerary generated on the fly, so the tool never simply fails on
  an unrecognized place.
- If your budget can't realistically cover the trip, the API returns a clear
  error with a full cost breakdown (transport / accommodation / activities &
  food) and a recommended budget instead of silently generating a plan you
  can't afford.

### Adaptive replanning
- Simulate a disruption — a flight delay, heavy rain, traffic, or a closed/
  overbooked attraction — either with one click or by typing a free-text
  description.
- The engine can parse **multiple disruption keywords in a single
  description** (e.g. *"flight delayed and heavy rain"*) and resolves all of
  them together.
- Disruptions **cascade**: a delay pushes every later event in the day,
  closures swap in a destination-appropriate alternative, and each change
  comes with a plain-English explanation of what happened and why.
- Disruptions are **cumulative** — the engine always operates on the
  itinerary's current state, so a second disruption stacks on top of the
  first instead of resetting the plan.
- Undo (up to a configurable history depth) and a hard Reset back to the
  originally generated plan are both available at any time.

### Itinerary-aware chat assistant
The chat box reads the live session (destination, day count, budget, current
items, what's already been suggested) and can:
- Answer budget questions and suggest cheaper swaps
- Recommend attractions or restaurants it hasn't already suggested
- Explain *why* a particular item is scheduled where it is
- Suggest packing items and weather backups for the destination
- Directly edit the itinerary from natural commands, e.g.:
  - *"remove the museum visit"*
  - *"add scuba diving"*
  - *"replace the fort tour with a beach day"*
  - *"change time of dinner to 8:00 PM"*

### Interactive map
- Every itinerary item carries real `lat`/`lng` coordinates (curated
  destinations use real-world coordinates; anything else gets a deterministic
  synthetic layout so markers stay stable across regenerations).
- Leaflet-based map with colour-coded markers per day and a connecting route
  line.
- Two-way sync with the itinerary board: click a marker to highlight its row,
  click a row to fly the map to its marker.

### Budget panel
- Total budget, estimated cost, remaining budget, and usage percentage, with
  a progress bar and an explicit over-budget warning state.

### Board UI
- Delayed or changed rows get a coloured left border and a per-item "why this
  changed" note.
- Undo / Reset controls, drag-and-drop reordering within a day (the server
  recalculates times to stay chronological after a reorder), and
  mobile-responsive breakpoints.
- All styling lives in CSS classes — no inline styles generated by JS.

### Backend hardening
- Request validation via Pydantic (length/range constraints on every field,
  friendly error messages on bad input).
- Every endpoint is try/catch-safe and returns proper HTTP status codes.
- CORS is restricted to a configurable allow-list — no wildcard `*` origin.
- All tunables (CORS origins, data file location, undo depth, scheduling
  buffer, host/port) are environment variables, not hardcoded values.
- Itineraries persist to a JSON-file session store keyed by `session_id`, so
  a session survives a backend restart instead of living only in memory.

## Quickstart

**Requirements:** Python 3.9+ (any recent Python 3 works).

```bash
# 1. Install backend dependencies
pip install -r requirements.txt

# 2. Start the API (defaults to http://127.0.0.1:8000)
python main.py
```

Then open `index.html` directly in a browser, or serve it with any static
file server, e.g.:

```bash
python -m http.server 5500
# then visit http://127.0.0.1:5500/index.html
```

If your API isn't running at `http://127.0.0.1:8000/api`, point the frontend
at it before the page's script runs by adding this above the closing
`</head>` tag in `index.html`:

```html
<script>window.Wander Planner_API_BASE = "https://your-api.example.com/api";</script>
```

> **Heads up if you're using a live-reloading dev server** (VS Code "Live
> Server", `live-server`, browser-sync, etc.): by default the session store
> is written to your OS temp directory, specifically so it can't land in a
> folder your dev server is watching and trigger an unwanted auto-refresh
> right after you click Generate. If you set `Wander Planner_DATA_FILE` yourself,
> just avoid pointing it at the same folder you're serving the frontend from.

## Configuration

All configuration is via environment variables — nothing needs to be
hardcoded or rebuilt to change behavior.

| Variable | Default | Purpose |
|---|---|---|
| `Wander Planner_ALLOWED_ORIGINS` | `http://localhost:5500,http://127.0.0.1:5500,http://localhost:3000,http://127.0.0.1:3000,http://localhost:8080,http://127.0.0.1:8080` | Comma-separated CORS allow-list. Add your deployed frontend's origin here. |
| `Wander Planner_DATA_FILE` | `<OS temp dir>/Wander Planner_sessions_store.json` | Where itinerary sessions are persisted. Keep this outside any folder a live-reloading dev server watches. |
| `Wander Planner_MAX_UNDO_HISTORY` | `25` | How many prior states are kept for Undo. |
| `Wander Planner_BUFFER_MIN` | `20` | Minimum gap (minutes) enforced between consecutive itinerary items. |
| `Wander Planner_HOST` | `0.0.0.0` | Bind host — only used when running `python main.py` directly. |
| `Wander Planner_PORT` | `8000` | Bind port — only used when running `python main.py` directly. |

Example:

```bash
export Wander Planner_ALLOWED_ORIGINS="https://mytravelapp.com"
export Wander Planner_MAX_UNDO_HISTORY=50
python main.py
```

## API reference

All endpoints are prefixed with `/api`. All `POST` bodies are JSON.

### `POST /api/generate`
Create a new itinerary and session.

**Request**
```json
{
  "destination": "Goa, India",
  "days": 4,
  "budget": 50000,
  "preferences": ["beaches", "history"],
  "notes": "traveling with a toddler, vegetarian food only"
}
```
| Field | Type | Constraints |
|---|---|---|
| `destination` | string | 1–120 chars |
| `days` | int | 1–30 |
| `budget` | float | > 0, ≤ 10,000,000 |
| `preferences` | string[] | optional, defaults to `[]` |
| `notes` | string | optional, ≤ 500 chars |

**Response** — a serialized session (`session_id`, `destination`, `days`,
`items[]` with `lat`/`lng`, and a `budget` object), **or**, if the budget is
unrealistic for the trip, an error payload with a full cost breakdown and a
recommended budget instead of a generated itinerary.

### `POST /api/replan`
Apply a disruption to an existing itinerary.
```json
{ "session_id": "…", "description": "flight delayed 3 hours and heavy rain" }
```
Returns the updated session plus a human-readable `explanation` of what
changed. Disruptions are cumulative — this always operates on the itinerary's
current state, not the original plan.

### `POST /api/chat`
Send a message to the itinerary-aware assistant.
```json
{ "session_id": "…", "message": "remove the museum visit" }
```
Returns the assistant's reply, and — if the message was an edit command — the
updated itinerary state.

### `POST /api/undo`
Revert the itinerary to its previous state.
```json
{ "session_id": "…" }
```

### `POST /api/reset`
Discard all disruptions/edits and restore the itinerary exactly as it was
first generated.
```json
{ "session_id": "…" }
```

### `POST /api/reorder`
Reorder items within a single day; the server recalculates times to keep the
day chronological.
```json
{ "session_id": "…", "day": 2, "ordered_ids": ["item_3", "item_1", "item_2"] }
```

### `GET /api/session/{session_id}`
Fetch a session's current serialized state — useful for reloading a session
after a page refresh.

### `GET /api/health`
```json
{ "status": "ok" }
```
Simple liveness check.

## Architecture notes

- **Persistence** is a single JSON file (`_load_db` / `_save_db` in
  `main.py`), not a real database. Perfectly fine for a prototype or demo —
  swap those two functions for a real DB call if you outgrow it.
- **The "AI" is a rules engine**, not a hosted LLM call. Disruption detection
  works off keyword matching (`flight`/`delay`/`late`, `rain`/`weather`/
  `storm`/`flood`/`snow`, `traffic`/`congestion`/`jam`,
  `closed`/`overbook`/`cancel`/`shut`), and chat responses are generated from
  the same structured destination/preference data driving the itinerary
  itself — so the reasoning text always stays consistent with the actual
  plan. Swapping `replan_items()` / `handle_chat()` for real model calls is a
  natural next step if you want more open-ended language understanding.
- **Coordinates** for curated destinations are real; everything else uses a
  seeded jitter function (`_jitter`) so the same location name always maps to
  the same synthetic point across regenerations, keeping the map visually
  stable.

## Known limitations

- Single JSON file for persistence — not concurrency-safe under heavy load,
  fine for local/demo use (a threading lock guards read-modify-write, but
  it's not a substitute for a real database under real traffic).
- No authentication — anyone with a `session_id` can read or modify that
  session. Fine for a local prototype; add auth before deploying publicly.
- No hosted LLM — natural-language understanding in chat and replanning is
  keyword/rule-based, not open-ended.
- INR-only, and only seven destinations have hand-curated content — every
  other destination falls back to a synthetic but plausible itinerary.

## Troubleshooting

**"Error connecting to backend"** — Confirm `python main.py` is running and
reachable at the URL shown in the message. If you're serving the frontend
from a different origin/port than the default allow-list, add it to
`Wander Planner_ALLOWED_ORIGINS`.

**CORS errors in the browser console** — The frontend's origin isn't in
`Wander Planner_ALLOWED_ORIGINS`. Add it (comma-separated) and restart the
backend.

**Page reloads right after clicking "Generate"** — This was a known issue
caused by the session store defaulting to a path next to `main.py`, which a
live-reloading dev server would pick up as a file change and refresh the
page. It's fixed by default now (session data lives in the OS temp
directory), but if you've set `Wander Planner_DATA_FILE` manually, make sure it's
not pointing inside the folder you're serving the frontend from.
